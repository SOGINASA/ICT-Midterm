# TengeFlow: сценарий защиты

TengeFlow — приложение для учёта повседневных расходов в тенге. Frontend построен на React, TypeScript, Tailwind и Zustand. Собственный Python backend использует Flask, SQLAlchemy и миграции Alembic. Локальная база — SQLite; для размещения предусмотрен PostgreSQL. Supabase в текущем приложении не используется.

## Короткая демонстрация

1. Покажите главную: назначение проекта, иллюстрации, превью кабинета и мобильную компоновку.
2. Зарегистрируйте тестовый аккаунт и откройте письмо в локальном inbox. Объясните, что разработческий inbox заменяет отправку почты, а production требует SMTP.
3. Пройдите настройку: имя, месячный бюджет, пять лимитов. Обратите внимание на проверку суммы лимитов и пустую историю нового аккаунта.
4. Добавьте расход, покажите изменение остатка, найдите запись в истории. Продемонстрируйте редактирование и удаление с подтверждением.
5. Покажите бюджеты и аналитику: все экраны используют одни записи, поэтому суммы согласованы.
6. Перезагрузите страницу, выйдите и войдите снова: сервер сохраняет аккаунт и данные; повторная настройка не требуется.
7. При необходимости откройте **Try demo**. В свежем демо бюджет составляет ₸120 000, расходы — ₸77 650, остаток — ₸42 350. Демо отдельно от аккаунта; его офлайн-очередь имитируется в браузере.

## Вопросы и ответы

**Какова основная функция?** Быстро записать расход и увидеть его влияние на месячный бюджет. Время заполнения в 15 секунд — проектная цель, а не результат проведённого исследования.

**Зачем нужен backend?** Он хранит аккаунты и общие для устройств финансовые данные, проверяет пароль, управляет сессиями и разрешает доступ только владельцу. Статический frontend сам по себе этого не обеспечивает.

**Почему Flask?** Такой подход соответствует другим проектам автора: Python API, SQLAlchemy-модели, явные маршруты и миграции. Интерфейс работает через репозиторий, поэтому детали хранения не попадают в компоненты React.

**Что отличает аутентификацию от авторизации?** Аутентификация проверяет личность. Авторизация определяет, какие записи этой личности разрешено читать и изменять. Сервер проверяет владельца каждого расхода независимо от интерфейса.

**Как устроена сессия?** Короткоживущий access token хранится в памяти frontend. Для обновления используется `HttpOnly` cookie; refresh token хранится на сервере в виде хеша и меняется при обновлении. Одноразовые ссылки подтверждения и восстановления также проверяет сервер.

**Что происходит после регистрации?** После подтверждения email новый пользователь задаёт имя, месячный бюджет и лимиты. Backend сохраняет всё одной транзакцией. Повторный запрос после потери ответа не сбрасывает уже завершённые настройки.

**Что происходит без сети?** В аккаунте загрузка и сохранение требуют соединения. При ошибке форма сохраняет черновик и не объявляет запись успешно сохранённой. В демо доступно локальное сохранение и демонстрационная смена `pending` на `synced`. Это не настоящая серверная синхронизация.

**Это PWA?** Есть мобильная адаптация, manifest и иконки. Service worker не реализован, поэтому гарантировать запуск или перезагрузку без сети нельзя.

**Как обеспечивается точность сумм?** Клиент и сервер валидируют диапазон и максимум два знака после запятой; расчёты учитывают минимальные денежные единицы. Доходы и банковские операции автоматически не импортируются.

**Что делает Vercel?** Раздаёт HTML, CSS и JavaScript. Маршруты `/api` перенаправляются на отдельно размещённый Python backend. Для публикации аккаунтов нужны постоянная база, серверное окружение и SMTP; внешний deployment этой версии ещё не выполнен.

**Какие ограничения остаются?** Ручной ввод, одна валюта KZT, пять категорий, общие настройки месячного бюджета без истории разных месячных лимитов, отсутствие банковской интеграции и офлайн-синхронизации аккаунта.

## Связь с ICT

- **Computer systems:** браузер выполняет JavaScript; память хранит активное состояние, диск — локальную или серверную базу.
- **Software:** frontend отвечает за представление, API — за правила и доступ, база — за постоянное хранение.
- **HCI:** короткая форма, понятные подписи, сохранение черновика, ошибки у полей и подтверждение удаления.
- **Networks:** HTTP используется локально, HTTPS требуется для опубликованного приложения; JSON связывает клиент и API.
- **Cloud:** Vercel размещает frontend, отдельный хостинг — Python backend и PostgreSQL.
- **Mobile:** адаптивная компоновка, нижняя навигация и поля для сенсорного ввода.
