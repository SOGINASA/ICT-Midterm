# Архитектура backend TengeFlow

TengeFlow использует собственный Flask API, SQLAlchemy и Alembic/Flask-Migrate. Подход соответствует проектам `sqo_cs2` и `erik`: отдельный Python backend с моделями, маршрутами и миграциями. Локальная база — SQLite, production-конфигурация поддерживает PostgreSQL. Supabase и его SDK больше не участвуют в работе приложения.

## Граница frontend и API

```text
Публичные страницы → авторизация или явный выбор демо
                               ↓
                Workspace → отдельный Zustand store
                               ↓
                       FinanceRepository
                       /               \
        LocalFinanceRepository     ApiFinanceRepository
                ↓                         ↓
           localStorage                /api
                                          ↓
                           Flask → SQLAlchemy → база

Профиль: onboardingCompleted=false → /onboarding → атомарное сохранение
         onboardingCompleted=true  → /app
```

[`Workspace.tsx`](../src/components/Workspace.tsx) создаёт store для текущей личности. Демо использует локальный репозиторий, аккаунт — `ApiFinanceRepository(expectedUserId)`. Незавершённый запрос старого аккаунта не должен обновлять состояние нового. Типы данных, расчёты и формы остаются общими.

Контракт описан в [`financeRepository.ts`](../src/services/financeRepository.ts), HTTP-адаптер — в [`apiFinanceRepository.ts`](../src/services/apiFinanceRepository.ts). [`apiClient.ts`](../src/services/apiClient.ts) отвечает за запросы и обновление сессии.

| Операция | Серверное поведение |
| --- | --- |
| Загрузка snapshot | Профиль, пять категорий и расходы текущего пользователя |
| Завершение настройки | Проверка имени, бюджета и лимитов; сохранение одной транзакцией |
| Добавление расхода | Проверка данных и категории; создание записи владельца с серверным ID |
| Изменение и удаление | Поиск записи с ограничением текущим пользователем |
| Изменение бюджета | Обновление собственных общего или категорийного лимитов |
| Повтор настройки | Возврат уже завершённого результата без перезаписи |

Клиент проверяет данные через Zod; сервер независимо проверяет входные значения и владельца. ID пользователя из тела запроса не определяет права доступа. UI обновляет подтверждённые финансовые данные после успешного ответа сервера. Недоступность сети не включает скрытый переход к демо.

## База и настройка аккаунта

Модели находятся в [`backend/tengeflow/models.py`](../backend/tengeflow/models.py), миграции — в `backend/migrations/`. Изменения схемы применяются через `flask --app app db upgrade`.

| Таблица | Назначение |
| --- | --- |
| `users` | Email, хеш пароля, профиль, бюджет и флаг завершения настройки |
| `categories` | Пять категорий и личные лимиты пользователя |
| `transactions` | Расходы, владелец, категория, способ оплаты, дата и заметка |
| `auth_sessions` | Сессии и хеши refresh tokens |
| `auth_codes` | Хеши одноразовых кодов подтверждения и восстановления |

После регистрации создаются профиль и категории без демонстрационных расходов. Новый пользователь сначала подтверждает email, затем проходит три шага настройки. Сервер сохраняет имя, бюджет, все лимиты и флаг завершения в одной транзакции. Ошибка откатывает изменение целиком. Повтор после потерянного ответа не сбрасывает уже завершённые настройки.

Имя содержит 2–60 символов. Первичный бюджет положителен; лимиты неотрицательны и суммарно не превышают бюджет. Деньги ограничены ₸1 трлн и двумя десятичными знаками. Категорий ровно пять: Food, Transport, Study, Leisure, Other. Заметка расхода ограничена 120 символами. Категория расхода принадлежит тому же пользователю.

В отличие от прежнего BaaS-подхода, авторизация выполняется собственным API. SQLAlchemy-запросы ограничиваются владельцем, определённым из проверенной сессии; база не открывается браузеру напрямую.

## Авторизация

Access JWT хранится только в памяти frontend и действует 15 минут. Refresh token передаётся через cookie `HttpOnly`, обновляется с ротацией и хранится на сервере в виде хеша; обычная refresh-сессия рассчитана на 14 дней. В production cookie использует `Secure`; frontend обращается к `/api` на своём origin через прокси.

Клиент объединяет параллельные запросы обновления сессии. Проверка личности и версии сессии препятствует повторной отправке запроса прежнего аккаунта от имени нового. Logout отзывает серверную сессию. Сброс пароля также контролируется сервером; одной браузерной отметки о восстановлении недостаточно.

Ссылки подтверждения и восстановления содержат одноразовые коды, хеши которых сохраняются в базе. Подтверждение email действует 24 часа, восстановление — 15 минут. Recovery-сессия ограничена восстановлением пароля и не даёт обычного доступа к финансовым данным.

Origin проверяется по разрешённому списку. Ограничения частоты запросов работают через Flask-Limiter: в разработке допустимо хранение в памяти, production требует общий Redis. Секреты остаются в окружении Python backend.

## Хранение в браузере

| Данные | Хранение |
| --- | --- |
| Демо-расходы | `localStorage`, ключ `tengeflow.finance.v1` |
| Демо-черновик | `localStorage`, ключ `tengeflow.expense-draft.v1` |
| Финансовые данные аккаунта | Память store и серверная база |
| Черновик расхода аккаунта | `sessionStorage`, отдельный ключ пользователя |
| Черновик настройки | `sessionStorage`, `tengeflow.account.<id>.onboarding.v1` |
| Access JWT | Только память; не `localStorage` |
| Refresh token | Cookie `HttpOnly` |

Черновик настройки сохраняется до подтверждённого завершения. Он помогает продолжить форму после перезагрузки, но не заменяет серверный флаг. Выход очищает черновики текущего пользователя. Демо и аккаунт не обмениваются расходами автоматически.

## Запуск, проверка и ограничения

Локальный `npm run backend:start` подготавливает Python-окружение, применяет миграции и запускает API. `backend:stop` сохраняет базу. Разработка использует локальный inbox; production — SMTP. Команды и адреса — в [LOCAL_BACKEND.md](LOCAL_BACKEND.md), размещение с PostgreSQL, Redis, Gunicorn и Vercel — в [BACKEND_SETUP.md](BACKEND_SETUP.md).

`npm run backend:test` запускает pytest и проверяет серверные правила; Jest — адаптер, состояние и формы; Playwright — пользовательские сценарии. Проверки аккаунта включаются через `RUN_ACCOUNT_E2E=1` и предназначены для локальной среды. Успешный локальный сценарий не подтверждает доставку production-писем или настройку опубликованного прокси.

Серверной офлайн-очереди нет. Если ответ на создание расхода потерялся, запись могла уже сохраниться; перед повтором нужно обновить историю. Идемпотентность расходов и разрешение конфликтов редактирования остаются отдельными задачами. Бюджеты — общие настройки, а не история лимитов для каждого месяца. Service worker и банковская интеграция не реализованы.
